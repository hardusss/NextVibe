## Sep 23 — OTA updates show the download screen and restart the app again
- fix(frontend): since the Sep 19 pending-intent change, a new OTA downloaded silently and only applied on the next cold start: no "Downloading update..." screen, no automatic restart (Android preview and iOS production alike). Cause: expo-updates checks and downloads by itself at every launch and runs one job at a time, so Splash's `checkForUpdateAsync()` waited for that whole download and hit its 3 s cap. Splash now reads the native launch state (`src/navigation/launchOta.ts`), so an update found at launch opens the update screen within the same 3 s cap. The update screen shows the real download progress and restarts the app once the update is on disk (`fetchUpdateAsync()` waits for the launch download and finds the update there). A pending push tap or deep link still defers the update to the next launch. JS only (OTA). The first OTA with this fix still applies silently; the ones after it show the screen.
- Tests: 12 new jest (`launchOta.test.ts`), jest 130/130, `tsc` clean; the production Android bundle exports, with `latestContext` compiled as a live binding.

- **One id per meeting, no new table.** A tap already writes two mirrored `Reputation` rows (one per person, one transaction). Both now carry the same `meet_slug`: 12 base62 characters of an HMAC (keyed by `SECRET_KEY`) of what makes a meeting unique: the pair plus the UTC day for IRL taps (Tap to Meet allows one per pair per day), the pair plus the event for event taps. It can't be guessed or enumerated, and two requests that race (both people pressing Confirm at once) land on the same meeting. `process_irl_tap` / `process_nfc_connect` write it and return `meet_slug` + `meet_url`. The "already met" answers (`ALREADY_TAPPED_TODAY`, already connected at this event) name the existing meet, so the phone that lost the race can still share. The backfill groups old rows the same way (rows of one tap that straddle midnight stay together), only fills empty slugs (a stored slug never changes), prints how many rows it set, and gives the same slugs on every run.

## Sep 22 — App Store review fixes (iOS 1.0.10) + push token sync
- Removed "audio" from UIBackgroundModes (Guideline 2.5.4). The list is now just `remote-notification`. `bluetooth-central` and `bluetooth-peripheral` went too: Bluetooth only runs while the app is open (the scanner stops on background, broadcasting runs only on a share screen). expo-video adds "audio" for background playback and PiP, and switching those options off would change the Android manifest, so a new iOS-only plugin, `withStripIosKeys.js`, strips it. It is listed first in `plugins` because Info.plist mods run in reverse order; listed last, it left "audio" in place.
- Rewrote all iOS purpose strings with concrete usage examples; removed unused permissions: Face ID (`NSFaceIDUsageDescription`, added by expo-secure-store, which the app never uses with `requireAuthentication`) and location Always (`NSLocationAlwaysUsageDescription`, `NSLocationAlwaysAndWhenInUseUsageDescription`; location is foreground only) (Guideline 5.1.1(ii)). The microphone string stays because a chat video shot with the camera records sound. Photo library add stays because "Save Image" in the share sheet (Seeker card) needs it. No NFC string: iPhones receive taps through iOS's own tag reading, which asks for nothing.
- supportsTablet: false.
- Expo push token now re-synced on every launch and after wallet sign-in; backend clears a token reused by another account. Fixes 104 DeviceNotRegistered tokens found on Sep 21.
- How the sync works: `syncPushToken()` (`src/notifications/pushToken.ts`) runs from `usePushTokenSync(userID)` in the root layout, so every sign-in (email, Google, Apple, MWA wallet, LazorKit) triggers it the same way, and again on foreground once a day. It never prompts; the launch prompt stays where it was. It compares the token with the `nv:pushToken` cache and with the new `GET /api/v1/users/me/push-token/`, and POSTs only when they differ. Each step times out after 5 s, and failures are logged and retried on the next launch. Signing out (Settings or the ban screen) sends `{pushToken: null, releaseToken}`, so the phone stops getting that account's pushes; signing out on an old phone leaves the newer phone's token alone. The old token listener is gone: it saved raw APNs/FCM device tokens as if they were Expo tokens. The backend now rejects anything that isn't an Expo push token. ⚠️ No backend migration.
- Scope: frontend (iOS config + JS) and backend. Android gets the JS as an OTA on its current binary: `runtimeVersion` stays `0.0.2-events`, and `expo prebuild` output for Android is byte-identical. Files: `app.config.js`, `withStripIosKeys.js`, `app/_layout.tsx`, `hooks/usePushTokenSync.ts`, `src/notifications/pushToken.ts` (+ tests), `components/Settings/PageSettings.tsx`, `components/UserBannedPage.tsx`, `src/api/save.push.token.ts` (removed); backend `user/views_pac/save_push_token.py`, `user/urls.py`, `user/tests_push_token.py`.
