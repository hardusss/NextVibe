# CLOCK IN Hackathon Changelog (Sep 8 – Oct 8, 2026)

All work below was built during the hackathon window. Format: date · scope · summary · key files.

## 2026-09-15
- fix(frontend/native): follow-up to the tap rework after a full diff review — ⚠️ still needs the native rebuild. (1) **iOS: the tap sheet never appeared over native modal screens** (event check-in, Tap to Meet opened from it, deposit…) because a React Native `<Modal>` presents from the root view controller, which UIKit refuses while a stack modal is up; the store then stayed "busy" and ignored every later tap until restart. The sheet now renders in a react-native-screens `FullWindowOverlay` on iOS (Android keeps `Modal`), and the store self-recovers from any flow that hasn't moved for 3 minutes. (2) Dedup is now by person, not only by rotating code: "Not now" silences that person for 90s, the preview-stage "already met"/"self" rejections (the backend returns them before saying who it is) are shown at most once per 10 minutes and are silent right after a meet, and the organizer's rotating check-in code opens the check-in screen once per event (10 min). (3) Neighbours no longer re-trigger each other: scanner success cooldown 15s, the broadcaster reports one read per device per code (was every reconnect — inflated "phones reached", repeated "They picked you up"), and a closed Bluetooth error stays quiet 15s (NFC/link taps 2s). (4) Code renewal can no longer reschedule itself after it was stopped (generation guard), and the check-in sheet re-checks it's still open after each await and cleans up on unmount. (5) Both people pressing Confirm together: the loser's "already connected" becomes a success; with a Tap to Meet screen open the prompt hands success to the screen instead of stacking a second one. (6) Networking with a slow GPS now says "Couldn't find your location" (not "allow location"), and Try again takes a fresh fix. (7) Solana Pay tap deposit is NFC-only and Android-only (Bluetooth delivered it to NextVibe phones that drop it while the sheet said "sent"); tap deposit shows the readiness checklist. (8) Status says "Not live — fix the item below" when Bluetooth is off/denied instead of "Live". (9) Android 15 no longer disables the sharing phone's own NFC reading. (10) Settings copy "You earned +20 Reputation points!" → "+20 reputation added to your profile!". New `promptStore` unit suite (11 tests: confirm flow, busy drop, per-person decline, Bluetooth error quiet window + retry, simultaneous confirm, silent already-met, symmetric close, once-per-event check-in, success hand-off, stuck recovery, foreign links) — jest 34/34 (`moduleNameMapper` for `@/`), tsc clean, iOS `BleShare` rebuilt, Kotlin recompiled against stubs + NFC reader simulation, iOS/Android bundles export. Audit findings fixed: (1) **iOS broadcaster never saw reads** — the GATT characteristic had a cached value, so CoreBluetooth answered reads itself and `didReceiveRead` never fired ("phones reached"/"taps detected" stuck at 0); it is now dynamic (value served on demand, rotations swap the payload without restarting advertising), with one long-lived `CBPeripheralManager`, `didAdd`/`didStartAdvertising` error events. (2) **Android could not broadcast over Bluetooth at all** (`startBroadcasting` was a no-op) — Android now runs a GATT server + connectable advertisement (`BLUETOOTH_ADVERTISE`), so iPhone↔Android and Android↔Android work over Bluetooth, with NFC as a second channel. (3) **Proximity gate −35 dBm on both platforms** meant phones had to be pressed back to back and cases often blocked it — replaced by an averaged RSSI over ≥2 samples, closest-phone-wins selection window (350ms), and two sensitivities: passive −50 (app-wide scanner) / active −62 (while a tap screen is open). (4) **A second tap with the same person silently did nothing** — native kept a per-session "already read" set and JS marked the token seen before the server answered; now native uses short per-device cooldowns (8s after a read, 1.5s after a failure) and JS dedup windows depend on how the prompt ended (failed → retry in 2s, declined → 30s, met → 10min, rotated tokens from someone already met are dropped quietly). (5) Scanner robustness: iOS 6s connect timeout (a pending connect used to wedge that phone for the session), Android `TRANSPORT_LE` (status 133 on dual-mode phones), `onScanFailed` handling, and a 4-starts-per-30s guard under Android's silent scan throttle; `BLUETOOTH_SCAN` is now `neverForLocation` so Android 12+ no longer needs Location switched on to find phones. (6) Android NFC tag emulation: APDU parsing by instruction (SELECT with/without Le, any READ BINARY length, bounds-checked), long NDEF records and URI prefix compression, one read event per tap, the service is disabled by default (it used to answer `https://nextvibe.io` in the background from install), `CardEmulation.setPreferredService` while sharing, reflective `setDiscoveryTechnology` on Android 15+ so the sharing phone doesn't read the other phone and navigate away, NFC state API + change events, `uses-feature` NFC/BLE `required="false"` (Play no longer hides the app from phones without NFC). Unused Expo template WebView/boilerplate removed from `nfc-send`. (7) **One receive experience**: Bluetooth discoveries, NFC tag reads and tap links all go through `src/proximity/promptStore.ts` → a single bottom sheet `ProximityPrompt` ("Phone detected" → "Meet @user?" with mode chip and REP → "You met @user"), instead of a BLE modal vs. two NFC full screens; OS links are intercepted in `+native-intent.ts` so a cold start from an NFC tap boots normally with the sheet on top (no screen without a back stack); check-in tokens hand over to the check-in screen with `post_id` (the BLE path used to drop it, so the POAP mint never started and Tap to Meet opened in IRL mode). (8) **Human errors**: `src/proximity/errors.ts` maps every backend string/code (`detail` bodies, `ALREADY_TAPPED_TODAY`, `IRL_DAILY_LIMIT`, geofence, expired code, check-in gate, 401/404/429/5xx, offline, timeout) to a title + what-to-do message + action (Try again / Open Settings / Sign in / Meet outside the event). (9) **Location never hangs a tap**: cached fix first, fresh fix capped (2.5–8s), permission asked only when the geofence needs it; check-in treats only `verified === true` as success (an unregistered user used to see "Checked in"). (10) **Tap to Meet screen**: broadcasts and listens at the same time (works whichever person opened it, or both — if the other side confirms first the pending "Meet them?" sheet closes itself), keeps the screen awake, "They picked you up — waiting for them to confirm" state from read events with fast polling, honest live/shaky/offline status, token renewal retries with backoff and stale detection (renewals used to fail silently while an expiring code stayed on air), refresh on return to foreground, a fix-it checklist (`useProximityReadiness`: Bluetooth off/denied/unsupported, NFC off, nearby detection paused in Settings, Location off on Android ≤11 — each with a fix button), three-step "how to tap" card, and generate errors with Retry or "Meet outside the event" instead of a dead end; the polling baseline no longer reports old connections as a new meet when the first fetch failed; a late "Keep tapping" start can't leak a broadcast after leaving. Organizer check-in sheet, profile share and tap deposit use the same broadcast/readiness hooks (both channels on Android, real read counts on iOS). The app-wide scanner runs only while signed in, asks for Bluetooth once, and no longer stops on iOS "inactive". `safeBack` replaces bare `router.back()` in event screens. ## 2026-09-14
- fix(frontend): the receiver's BLE confirmation could spin forever or re-prompt repeatedly after the meet was already handled. Four compounding causes: (1) no JS-side dedup existed at all (the `modules/ble-share/session.ts` comment claimed a "time-based debounce in useBleScanner" that was never written), and the native per-device dedup (`readDeviceIds`/`readAddresses` + 3s debounce) was wiped on every `stopScanner()` — which the discovery handler called on *every* discovery before restarting 800ms after accept or immediately on decline, so the same peer re-fired the modal in a loop; (2) none of the proximity axios calls had a timeout, so a network stall left the modal's "Loading details…" or the receive screen's "connecting" state spinning forever; (3) `EventNFCReceiveScreen`'s legacy `handleConnect` success branch had no `else` — a 200 with `success:false` stranded the screen in "connecting" — and neither connect handler had an in-flight guard, so a double-tapped "Confirm Meet" could fire two granting calls; (4) `NfcCheckinSheet`'s BLE read handler had no debounce (the NFC one did) and its stale-closure `isBroadcasting` guard allowed double-registered listeners on rapid re-presents. Now: the scanner keeps running through a discovery (native dedup survives), a module-level token→lastSeen map with a 60s TTL (> the 50s rotation) guarantees one prompt per unique token — decline included — a `processingRef` drops discoveries while a prompt is up, accept/decline fully clear `scannedPath`/`details`/`loadingDetail`, all generate/verify/preview calls get a 12s timeout with a distinct timed-out message, both connect handlers are idempotent via `inFlightRef` + try/finally, the missing `else` surfaces "Connection failed" with a new Try Again CTA, the sheet's BLE reads share the 2s debounce and its guard became a ref that removes any existing listener before registering, and the deep-link `u/e.tsx` preview is guarded against double-fire. 3 new client unit tests (see the mode-resolution entry); `tsc --noEmit` clean.
